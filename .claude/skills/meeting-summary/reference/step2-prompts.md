# Step 2: LLM 提炼 Prompt 模板

## JSON Schema

分析文字稿，**只输出以下 JSON，不加任何其他文字**：

```json
{
  "title": "会议主题（≤20字）",
  "date": "YYYY-MM-DD",
  "duration": "45分钟",
  "participants": ["张三", "李四", "王五"],

  "mindmap": "# 会议主题\n## 议题一\n### 要点 A\n### 要点 B\n## 议题二\n### 要点 C\n## 待办事项\n### 任务 A\n### 任务 B",

  "summary": [
    {
      "topic": "议题名称",
      "content": "核心内容，完整描述议题要点，可多句。核心关键词**内嵌**正文中（每段3-5个），如 `复购率` `毛利率45%` `哑铃型组织`。**禁止**在正文末尾单独列出 '关键词：`A` `B`' 格式"
    }
  ],

  "decisions": [
    {
      "content": "决策内容，必须完整保留原文关键信息，不得压缩或省略数字、条件、案例。如'活动毛利率不低于45%，综合底线30%'必须保留两个数字",
      "owner": "负责人（未提及写 TBD）",
      "timestamp": "01:23"
    }
  ],

  "todos": [
    {
      "task": "任务描述（动词开头），包含足够上下文，不得压缩。如原文有具体验收标准或数量要求，完整写入 task 描述",
      "owner": "负责人（未提及写 TBD）",
      "due": "YYYY-MM-DD（未提及写 null）",
      "priority": "high|medium|low",
      "timestamp": "来源时间戳"
    }
  ],

  "risks": [
    "风险描述（≤30字）"
  ],

  "tags": [
    "标签1", "标签2", "标签3"
  ]
}
```

## 提炼规则（12 条）

**① 人物完整性**：会议中提到的每一个人（包括外部合作者、被讨论的第三方），都必须在 summary 或 mindmap 中体现其角色定位，不得遗漏。

**② 数据精确性**：所有数字（金额、百分比、人数、日期）必须原样保留，不做模糊化。如出现"邢台订单400万只拿了200万"，必须完整保留两个数字。

**③ 因果链条**：问题+原因必须完整记录。例如"复购率低 → 服务质量差（具体案例）+ 活动后无客情维护（无节日问候、无回访）"。

**④ 具体案例不泛化**：原文提到的具体项目名称、客户案例、金额，在涉及业务策略的部分应保留，不替换为"某项目""某客户"。

**⑤ 转录纠错**：自动识别并纠正明显的转录错误，如"商务线索词"→"商务线索数"、人名前后不一致时统一最可能的写法。

**⑥ 思维导图结构（以人物为主线）**：mindmap 以参会的核心人物为骨架组织。中心节点（#）为会议主题，二级节点（##）为每位关键参会人，格式为"姓名·角色"（如"花花·决策者""凯西·商务负责人""亚龙·数据中台"），三级节点（###）为该人在会议中的核心职责、决策或任务（2-4条）。若多人共同负责同一事项，在各自节点下分别体现视角。mindmap 字段使用 Markdown 标题层级（`#` `##` `###`），最多 3 层，不使用时间顺序。

**⑦ 议题摘要深度**：每个议题摘要包含：核心结论/决策（1句）+ 背景和原因（1-2句）+ 具体数据或案例（如有）+ 不同发言人视角（如有，注明来源）。

**⑧ 待办可执行性**：每条 todo 必须是可执行的，包含：做什么（具体动作，动词开头）+ 谁来做 + 做到什么程度（验收标准，如有）。如原文有具体要求（如"招一个有主编能力的人，能出全年排期和OKR，能策划爆款"），写入 task 描述中。

**⑨ 决策 vs 待办区分**：已确定的事实 → decisions；需后续行动 → todos。不混用。

**⑩ participants**：**只包含在会议中实际发言的说话人**（即转录中有台词的人），不包含会议中被提及或讨论的外部人员、客户、合作伙伴等。
- **优先**：用户触发时若提供了说话人映射（如「说话人0=wenshan，说话人1=亚龙」），直接按映射替换，不再从上下文推断
- **其次**：若无映射，从称呼、自我介绍或上下文推断真实姓名（如"花花你好"、"我是凯西"、"亚龙你来说"）
- **兜底**：无法推断时保留说话人0/1/2等标签

**⑪ 不捏造**：不捏造未在文字稿中出现的内容。
- `priority`：截止日期近或明确强调 → high；一般跟进 → medium；其余 → low

**⑫ tags（必填）**：从会议内容中提炼 5-8 个相关标签，反映会议主题、行业领域、关键议题、参与方、项目名称等。要求：
- 固定包含 `会议纪要`、`meeting-summary` 两个基础标签
- 其余 3-6 个来自会议实际内容（项目名、行业词、关键动作、人名/公司名等），不得重复或泛化
- 标签用中文或英文均可，**不加 `#` 前缀**（代码生成时统一添加）
- 示例：`["会议纪要", "meeting-summary", "数据库设计", "独立站", "文化产品", "商业化"]`

## Step 2b：JSON 校验

检查 LLM 输出 JSON，若存在以下问题 → 追加 prompt 重试一次（最多 1 次）：

- **关键词尾巴**：任意 `summary[].content` 结尾匹配 `关键词[：:]` 模式

重试追加提示：「summary.content 末尾出现了独立的 '关键词：' 列表，这是格式错误。关键词必须内嵌在正文句子中，不得在末尾单独列出。仅重新输出完整 JSON，不加其他文字。」
